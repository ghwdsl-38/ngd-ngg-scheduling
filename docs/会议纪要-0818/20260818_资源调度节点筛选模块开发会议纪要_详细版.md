## 二、当前系统实现情况

### 2.1 总体架构

当前系统整体采用 **Go + Python 混合实现**：

- 左侧资源采集及 Controller 编排部分主要采用 Go 实现；
- Controller 负责整个算法流程的编排；
- 具体的资源筛选、节点选择和优化算法使用 Python 实现；
- Go 侧通过启动 Python Worker 子进程的方式调用算法模块；
- Go 与 Python 之间采用 JSON Lines/JSON 数据进行交互；
- 该设计主要是为了避免每个算法实例都独立保存一份大规模节点状态数据，从而降低额外内存开销。

当前实现思路可以概括为：

```text
需求 / CRD
   ↓
Go Controller
   ↓
资源数据聚合
   ↓
JSON
   ↓
Python Algorithm Worker
   ↓
候选节点 / 分组结果
   ↓
NGG
```

### 2.2 当前 Demo 情况

当前 Demo 在服务器上通过 Kind/Docker 运行。

由于单机环境无法真实启动 1000～3000 个 Worker 节点，因此目前采用两种方式：

1. **真实 Kubernetes/Kind 小规模环境**
   - 当前实际模拟约 9 个节点；
   - 用于验证整体控制流程是否能跑通。

2. **算法侧 Mock 大规模节点**
   - 在算法侧 Mock 1000 个左右的节点数据；
   - 用于验证算法对大规模节点输入的筛选逻辑；
   - 当前已经可以模拟 CPU、内存、交换机拓扑、节点状态等信息。

会议认为，现有 Demo 已经证明了整体流程基本可行，但目前测试方式偏“整体打包运行”，还不能满足后续工程验收对**模块级单元测试**的要求。

## 四、需要补充的三段单元测试

会议最终明确，当前阶段至少补齐三段独立测试。

### 4.1 单元测试一：CR/需求输入 → Controller → NGG/中间结果

#### 测试目标

验证 Controller 收到模拟需求后，能否：

1. 正确触发调谐逻辑；
2. 调用后端资源筛选接口；
3. 获得候选节点结果；
4. 生成符合约定格式的 NGG/CR 结果。

#### 输入

Mock 一个需求 CR，例如：

- 目标节点数量；
- CPU/内存需求；
- 拓扑约束；
- 机房/交换机约束；
- 其他调度约束。

#### 后端处理

后端资源接口可以先直接 Mock 返回固定数量的候选节点，例如：

```text
输入：需求 CR
输出：1000 个候选节点
```

#### 验收重点

- Controller 是否正确 watch/接收 CR；
- 是否正确进入 reconcile；
- 是否正确调用后端；
- 是否能生成 NGG；
- NGG 中候选节点数量是否符合预期；
- 数据结构是否满足 CRD 定义。

---

### 4.2 单元测试二：Mock REST 请求 → 资源聚合 → 算法执行

#### 测试目标

验证算法服务独立运行时，可以：

1. 接收 REST 请求；
2. 获取 Mock 的资源数据；
3. 将资源数据传入算法；
4. 执行节点筛选；
5. 返回正确的候选节点集合。

#### Mock 数据包括

至少需要构造以下几类数据：

##### 1. Prometheus 动态指标

包括：

- CPU 使用率；
- 内存使用率；
- 必要时增加历史 CPU/内存统计；
- 接口应模拟真实 Prometheus REST API；
- Mock 接口建议加入认证逻辑，因为真实环境 Prometheus 接口存在鉴权。

##### 2. 节点静态资源

包括：

- CPU 总核数；
- 内存总容量；
- 节点名称；
- 节点标签；
- 可分配资源；
- 节点状态等。

##### 3. 网络/拓扑静态数据

包括：

- 节点所属 Leaf Switch；
- Core Switch；
- 机房；
- 可用区；
- 节点与交换机的映射关系；
- 网络带宽或时延信息。

#### 验收重点

需要确认：

```text
Mock REST
   ↓
资源读取
   ↓
内存结构
   ↓
Python 算法
   ↓
候选节点
```

整条链路可独立运行。

### 4.3 单元测试三：3000 节点大规模筛选性能测试

#### 测试目标

验证算法在接近目标生产规模下的性能。

会议明确建议按照：

```text
原始节点：3000
最终候选：约1000
```

进行测试。

#### Mock 数据设计建议

例如构造 3000 个节点：

1. 第一阶段资源条件筛选：
   - 约 2000～2500 个节点满足基础 CPU/内存要求；
   - 其余节点因资源不足被过滤。

2. 第二阶段网络/拓扑筛选：
   - 根据交换机、机房、拓扑等条件继续筛选；
   - 最终保留约 1000 个节点。

3. 第三阶段：
   - 在满足硬性条件的候选节点上进行负载均衡、评分或排序。

#### 性能目标

会议提出：

- **优先目标：约 500 ms**
- **复杂情况下：1 s 内可以接受**

需要注意区分：

1. **纯算法计算时间**
2. REST 调用时间
3. Go/Python 通信时间
4. 数据序列化/反序列化时间
5. NGG 写入时间
6. 整体链路时间

当前讨论中已有约 3 秒级的测量结果，但该结果包含服务启动、同步内存、Mock 环境等额外开销，暂时不能直接作为最终算法性能结论。

因此下一轮测试必须单独统计：

```text
Algorithm Start
      ↓
筛选 / 排序 / 计算
      ↓
Algorithm End
```

的纯计算耗时。

## 六、节点筛选顺序

当前算法流程已经支持按配置编排不同算法。

会议讨论了一个重要问题：

> 节点筛选到底应该先按资源过滤，还是先按网络/拓扑过滤？

当前实现偏向：

```text
Requirement 资源约束
   ↓
Group / 拓扑约束
   ↓
负载均衡
```

会议中提出，如果网络拓扑是强约束，则可以考虑优先进行网络范围缩减，以减少后续计算量。

最终结论是：

- 当前架构已经支持调整顺序；
- 不需要重构系统；
- 后续算法确定后，只需修改 algorithm 编排配置/对应算法文件即可；
- 第一阶段先保证流程可配置、可替换，不急于确定最终最优顺序。

## 八、NGD / NGG 接口统一

### 8.1 当前问题

目前算法侧生成的 NGG 数据格式与另一侧已经设计好的 CRD 格式存在差异。

当前算法输出：

- 一个结果中可能存在多组候选；
- 目前支持 Top3；
- 真正被后端消费的字段主要是 Node Name。

而当前另一侧设计更倾向：

```text
1 个 NGD
   ↓
1 个 NGG
   ↓
1 组候选节点
```

### 8.2 第一版处理方式

会议决定第一版先简化：

- **Top3 改为 Top1**
- 一个 NGD 对应一个 NGG；
- 一个 NGG 内只保留当前指定的一组候选；
- 字段按照已经约定的 CRD 格式进行统一。

后续如确有必要，再扩展为：

- 一个需求对应多组候选；
- Top-K 备用方案；
- 多拓扑组等。

## 九、NGG 状态管理

会议特别讨论了 NGG 的生命周期。

### 9.1 不建议资源异常后直接删除 NGG

如果上游 Prometheus、网络拓扑或节点状态数据暂时获取失败，不建议直接：

```text
Delete NGG
```

然后恢复后重新 Create。

建议：

```text
NGG 保留
status = inactive
```

恢复后：

```text
status = active
```

这样可以减少：

- API Server 写压力；
- etcd 删除/创建开销；
- Controller 对资源对象的频繁重建。

### 9.2 Active 状态的作用

Status 同时可以用于故障定位：

- NGD 存在、NGG 不存在：
  - 可能表示生成 NGG 的 Controller 本身异常；

- NGD 存在、NGG 存在，但 `status != active`：
  - 可能表示 Prometheus、拓扑数据或外部依赖异常。

因此该状态不仅是调度可用性标识，同时也是运维诊断信息。

### 9.3 超时机制

建议 NGG 中增加：

- `status`
- `lastUpdateTime` / timestamp

例如：

```text
当前时间 - lastUpdateTime < 5 min
→ 认为数据仍有效

超过阈值
→ inactive
```

具体超时时间后续配置化。

## 十一、当前系统性能问题

会议认为，功能完成后下一步重点是性能。

### 11.1 当前可能存在的问题

- 数据结构层级较深；
- 树结构遍历可能在 3000 节点下产生额外开销；
- 多次校验；
- 多层 REST / IPC 调用；
- Go → Python 调用；
- 动态数据同步；
- 容器/Kind 环境额外开销。

### 11.2 优化原则

后续可以考虑：

1. 减少重复遍历；
2. 先使用强约束快速缩小候选集；
3. 静态拓扑常驻内存；
4. Prometheus 数据后台线程周期更新；
5. 调度热路径只读取缓存；
6. 减少 Go/Python 重复序列化；
7. 通过标签在 API Server 侧先过滤对象；
8. 避免每次重新加载所有节点数据；
9. 对大规模候选集设计高效索引结构。
