# 双 CRD 接口设计文档

> 本文档定义 A-B-C 三方协作模式下的两个 K8s CRD 接口：
> - **NodeGroupDemand (NGD)**：A（数据组/业务方）向 B（平台组 PRC）声明节点组需求
> - **NodeGroupGrant (NGG)**：B（平台组 PRC）向 C（数据组 Volcano 插件）授权可用节点组
>
> 两个 CRD 分属不同协作边界，各自独立演进。

---

## 1. 协作模型

### 1.1 三方角色

| 角色 | 职责 | 组件 |
|---|---|---|
| **A - 需求方** | 声明节点组需求（拓扑、标签、数量、配额） | 数据组/业务方 |
| **B - 供给方** | 按需求筛选节点 + 负载感知过滤/打分 + 持续维护授权 | PRC（平台组） |
| **C - 消费方** | 在授权节点组内做 Gang/Binpack/Queue 调度决策 | Volcano 插件（数据组） |

### 1.2 为什么需要两个 CRD

| 判断条件 | 是否满足 | 说明 |
|---|---|---|
| 产品有独立生命周期 | 是 | NGG 有 Active -> Reclaim -> Draining -> Returned 状态机 |
| 产品可脱离需求独立存在 | 是 | NGG 可由静态配置或手动创建，不强制依赖 NGD |
| B 和 C 之间有双向通信 | 是 | C 写 status.consumer 回传使用量和回收状态 |
| 更新频率差异大 | 是 | NGD 偶尔变更 vs NGG 每 15 秒刷新 |
| A 和 C 关注点不同 | 是 | A 关心"需求是否满足"，C 关心"哪些节点可用" |
| 产品需要独立版本化 | 是 | NGG 有 spec.version 契约版本管理 |

> 类比 K8s 的 PVC/PV 模型：PVC（需求）和 PV（产品）分离，中间通过绑定关系连接。

### 1.3 边界示意图

```
  A (需求方)                    B (供给方)                    C (消费方)
  数据组/业务方                 平台组 PRC                    数据组 Volcano
  ┌───────────┐               ┌───────────────┐             ┌───────────┐
  │           │  创建 NGD      │               │  创建 NGG    │           │
  │           │──────────────►│               │────────────►│           │
  │           │               │  筛选+过滤+打分 │             │  调度决策  │
  │           │  读 status     │               │  读 spec     │           │
  │           │◄──────────────│               │             │           │
  │           │               │               │  写 status   │           │
  │           │               │               │◄────────────│           │
  └───────────┘               └───────────────┘             └───────────┘

        NGD: A-B 接口               NGG: B-C 接口
```

### 1.4 数据流方向

| CRD | 方向 | 字段区域 | 写入方 | 读取方 | 内容 |
|---|---|---|---|---|---|
| NGD | A -> B | `spec` | A（需求方） | B（PRC） | 节点筛选条件、数量/配额上限 |
| NGD | B -> A | `status` | B（PRC） | A（需求方） | 处理状态、授权引用、已解析节点数 |
| NGG | B -> C | `spec` | B（PRC） | C（Volcano 插件） | 可用节点列表、负载评分、时效信息 |
| NGG | C -> B | `status.consumer` | C（数据组 controller） | B（PRC） | 使用量、回收排空状态、阻塞原因 |

双方各自只写自己的区域，不交叉写入。通过 CRD status subresource 和 Server-Side Apply field manager 实现字段级所有权隔离。

## 2. NodeGroupDemand CRD 定义

### 2.1 CRD 定义文件

完整 CRD YAML 已外置为独立部署文件，不在本文档内嵌，直接引用：

> [crd-deploy/nodegroupdemand-crd.yaml](crd-deploy/nodegroupdemand-crd.yaml)

### 2.2 CR 实例示例

```yaml
apiVersion: scheduling.platform.example.io/v1alpha1
kind: NodeGroupDemand
metadata:
  name: spark-zone-a-demand
spec:
  schedulerName: volcano
  nodeSelector:
    matchLabels:
      kubernetes.io/arch: amd64
    matchExpressions:
    - key: node-role.kubernetes.io/worker
      operator: Exists
  topologyLabels:
    topology.kubernetes.io/data-center: dc-bj-1
    topology.kubernetes.io/access-switch: 10.0.1.10
  maxNodes: 50
  quota:
    cpu: "500"
    memory: 2Ti
status:
  phase: Fulfilled
  grantRef: ngg-spark-zone-a
  resolvedNodeCount: 32
  lastUpdated: "2026-07-29T10:30:00Z"
```

### 2.3 字段说明

| 字段 | 作用 | 写入方 |
|---|---|---|
| `spec.schedulerName` | 目标调度器，PRC 据此创建对应 NGG | A |
| `spec.nodeSelector` | 节点筛选条件（label matchLabels/matchExpressions） | A |
| `spec.topologyLabels` | 拓扑硬性约束标签；value 具体标识=指定位置，`requiredSame`=同一位置（任意） | A |
| `spec.maxNodes` | 候选节点数量上限（可选） | A |
| `spec.quota` | 资源配额上限（可选） | A |
| `spec.minThroughput` | 最低吞吐量要求（5 分钟平均） | A |
| `spec.crossClusterAffinity` | 跨集群互访 IP 亲和约束 | A |
| `spec.intraClusterAffinity` | 本集群互访 IP 亲和约束 | A |
| `spec.minResources` | 节点组最小资源保障 | A |
| `spec.networkReachability` | 外部存储集群网络互通要求 | A |
| `spec.preferredSubnet` | 子网偏好（软性） | A |
| `status.phase` | 需求处理状态 | B（PRC） |
| `status.grantRef` | 关联的 NGG CR 名称 | B（PRC） |
| `status.resolvedNodeCount` | 实际解析到的节点数 | B（PRC） |
| `status.lastUpdated` | 最后处理时间 | B（PRC） |
| `status.message` | 状态/错误信息 | B（PRC） |

## 4. 两个 CRD 的关系

### 4.1 绑定关系

```
NodeGroupDemand (A 创建)          NodeGroupGrant (B 创建)
┌─────────────────────┐          ┌─────────────────────┐
│ spec:               │          │ spec:               │
│   schedulerName     │          │   schedulerName     │
│   nodeSelector      │          │   version           │
│   maxNodes          │          │   timestamp         │
│   quota             │          │   source            │
│                     │          │   demandRef ────────│──┐
│ status:             │          │   nodes[]           │  │
│   phase: Fulfilled  │          │                     │  │
│   grantRef ─────────│──┐       │ status:             │  │
│   resolvedNodeCount │  │       │   phase: Active     │  │
│                     │  │       │     consumer:       │  │
└─────────────────────┘  │       │     used/drain     │  │
                         │       └─────────────────────┘  │
                         │                                │
                         └────── 1:1 绑定 ────────────────┘
```

- NGD `status.grantRef` 指向 B 创建的 NGG（正向引用）
- NGG `spec.demandRef` 指向 A 的 NGD（反向溯源）
- 典型场景下 1:1 关系（一个 Demand 对应一个 Grant）

### 4.2 从 NGD 到 NGG 的处理流程

```
A 创建/修改 NGD          PRC (B) 处理                 K8s API Server         C (Volcano) 消费
     │                        │                            │                       │
     │──创建/修改 NGD CR──────►│                            │                       │
     │                        │                            │                       │
     │                        │──watch 到 NGD 变更          │                       │
     │                        │──解析 nodeSelector 等条件   │                       │
     │                        │──遍历集群 Node, 按 label    │                       │
     │                        │──读取负载数据快照           │                       │
     │                        │──负载过滤 + 打分 + 资源计算  │                       │
     │                        │──创建/更新 NGG CR──────────►│                       │
     │                        │──更新 NGD.status───────────►│                       │
     │                        │  (phase=Fulfilled,          │                       │
     │                        │   grantRef=ngg-xxx)         │                       │
     │                        │                            │                       │
     │                        │  (每 15s 持续更新 NGG)      │                       │
     │                        │──读取最新负载数据           │                       │
     │                        │──重新筛选+过滤+打分         │                       │
     │                        │──更新 NGG CR──────────────►│──informer 通知────────►│
     │                        │                            │                       │──OnSessionOpen
     │                        │                            │                       │  读 NGG, 构建候选集
     │                        │                            │                       │──FilterFn + ScoreFn
     │                        │                            │                       │──Gang/Binpack 编排
     │                        │                            │                       │──Bind Pod
```

### 4.3 NGG 的三种创建来源

NGG 不只有 NGD 一种创建路径：

| 来源 | 形式 | 创建方 | 适用阶段 |
|---|---|---|---|
| **NodeGroupDemand CR** | K8s CR，声明式 | A（数据组/业务方） | MVP，动态创建/修改/删除节点组 |
| **静态配置** | PRC 配置文件（YAML） | B（平台组运维） | MVP，固定的、长期不变的节点组 |
| **手动创建 NGG** | 直接 kubectl apply | B（平台组运维） | 临时调试、紧急扩容；PRC 检测到后接管维护 |

> MVP 阶段 NGD 简化实现：支持创建/删除触发 NGG 生命周期管理，status 回写为后续增强。

### 4.4 三种来源的对比

| 维度 | NodeGroupDemand CR | 静态配置 | 手动创建 NGG |
|---|---|---|---|
| 创建方 | 数据组/业务方 | 平台组运维 | 平台组运维 |
| 形式 | K8s CR（声明式） | YAML 配置文件 | K8s CR（完整 spec） |
| 节点筛选条件 | nodeSelector + maxNodes + quota | nodeSelector + maxNodes | 直接指定 nodes 列表 |
| 动态变更 | 修改 NGD CR 即可 | 修改配置文件 + PRC 重载 | kubectl edit/delete |
| 生命周期管理 | 创建/删除 NGD -> 创建/删除 NGG | PRC 启动/重载时管理 | 手动创建/删除 |
| demandRef 标记 | NGD CR 名称 | `static:<config-name>` | 空 或 `manual` |
| 适用阶段 | MVP | MVP | 调试/紧急 |

### 4.5 NGD 变更与删除

- **NGD spec 变更**（如修改 nodeSelector）：PRC 在下一次定时更新时用新条件重新筛选，更新 NGG。不删除重建。
- **NGD 删除**：PRC watch 到 NGD 被删除，删除对应的 NGG CR。
- **NGD status.phase** 变化不触发 PRC 重新处理，仅由 PRC 写入供 A 查看。

## 5. 字段所有权矩阵

### 5.1 NodeGroupDemand 读写权限

| 字段路径 | A（需求方） | B（PRC） | 说明 |
|---|---|---|---|
| `metadata` (除 ownerReference) | 读写 | 只读 | A 创建 CR，可修改 labels/annotations |
| `spec.schedulerName` | **写** | 只读 | A 创建时设定 |
| `spec.nodeSelector` | **写** | 只读 | A 按需修改 |
| `spec.topologyLabels` | **写** | 只读 | A 按需修改 |
| `spec.maxNodes` | **写** | 只读 | A 按需修改 |
| `spec.quota` | **写** | 只读 | A 按需修改 |
| `spec.minThroughput` | **写** | 只读 | A 按需修改 |
| `spec.crossClusterAffinity` | **写** | 只读 | A 按需修改 |
| `spec.intraClusterAffinity` | **写** | 只读 | A 按需修改 |
| `spec.minResources` | **写** | 只读 | A 按需修改 |
| `spec.networkReachability` | **写** | 只读 | A 按需修改 |
| `spec.preferredSubnet` | **写** | 只读 | A 按需修改 |
| `status.phase` | 只读 | **写** | PRC 更新处理状态 |
| `status.grantRef` | 只读 | **写** | PRC 写入关联 NGG 名称 |
| `status.resolvedNodeCount` | 只读 | **写** | PRC 写入 |
| `status.lastUpdated` | 只读 | **写** | PRC 写入 |
| `status.message` | 只读 | **写** | PRC 写入 |

### 5.2 NodeGroupGrant 读写权限

| 字段路径 | B（PRC） | C（Volcano 侧） | 说明 |
|---|---|---|---|
| `metadata` (除 ownerReference) | 读写 | 只读 | PRC 创建 CR |
| `spec.schedulerName` | **写** | 只读 | PRC 创建时设定 |
| `spec.version` | **写** | 只读 | 契约版本 |
| `spec.timestamp` | **写** | 只读 | PRC 每 15 秒更新 |
| `spec.source` | **写** | 只读 | PRC 根据负载可用性设定 |
| `spec.demandRef` | **写** | 只读 | PRC 创建时设定 |
| `spec.nodes` | **写** | 只读 | PRC 每 15 秒全量覆盖 |
| `spec.nodes[].topology` | **写** | 只读 | PRC 写入节点网络拓扑信息 |
| `spec.nodes[].resources.throughput5mAvg` | **写** | 只读 | PRC 写入 5 分钟平均吞吐量 |
| `status.phase` | **写** | 只读 | PRC 更新 |
| `status.resolvedCapacity` | **写** | 只读 | PRC 计算 |
| `status.consumer` | 只读 | **写** | 数据组写入 |
| `status.consumer.acceptedGeneration` | 只读 | **写** | 数据组写入 |
| `status.consumer.used` | 只读 | **写** | 数据组写入 |
| `status.consumer.drain` | 只读 | **写** | 数据组写入 |

### 5.3 实现方式

两个 CRD 均通过 K8s Server-Side Apply (SSA) field manager 实现字段所有权隔离：

- **NGD**：A 写 spec，PRC 写 status
- **NGG**：PRC 写 spec 和 status.phase/resolvedCapacity，数据组写 status.consumer
- 各方各自只 apply 自己的字段，不覆盖对方
- CRD 配置 `status: {}` subresource，确保 status 更新走独立的 API 路径

## 6. NGG 生命周期

### 6.1 创建

```
方式 1: PRC 根据 NodeGroupDemand CR 自动创建
        A 创建 NGD -> PRC watch 到 -> 筛选+过滤+打分 -> 创建 NGG -> 更新 NGD.status

方式 2: PRC 根据静态配置创建（MVP）
        PRC 启动 -> 读取配置 -> 创建 NGG

方式 3: 手动创建
        运维 kubectl apply ngg.yaml -> PRC watch 到后接管维护
```

无论哪种方式，NGG 一旦创建，PRC 即接管后续的持续更新（每 15 秒刷新 nodes/timestamp）。

### 6.2 维护

```
PRC 每 15 秒:
  1. 读取负载数据快照
  2. 根据该 NGG 关联的需求（demandRef）筛选候选节点
  3. 负载感知过滤 + 打分 + 资源计算
  4. 全量覆盖 spec.nodes, spec.timestamp, spec.source
  5. 更新 status.resolvedCapacity
```

### 6.3 回收（Phase 3）

```
Active (PRC 持续更新)
  │
  │  平台组决定回收（节点维护/资源调配）
  ▼
ReclaimRequested (PRC 更新 phase, 添加回收 taint)
  │
  │  数据组感知到
  ▼
Draining (数据组停止新增 executor, 优雅排空, 更新 status.consumer.drain)
  │
  │  排空完成 或 deadline 到达
  ▼
Returned (PRC 确认无批处理 Pod, 调整节点分类)
  │
  │  重新授权
  ▼
Active
```

### 6.4 删除

- NGG 被 PRC 主动删除：关联的 NGD 被删除或配置变更时
- NGG 被人工删除：kubectl delete，PRC 不再维护
- 删除后 Volcano 插件读不到该 NGG，候选集相应缩小

## 7. NGD 生命周期

### 7.1 状态流转

```
           A 创建 NGD
               │
               ▼
           Pending ──────► PRC 尚未处理
               │
               │  PRC watch 到，开始处理
               ▼
           Updating ─────► 正在筛选+过滤+打分
               │
               │  处理成功，NGG 已创建/更新
               ▼
           Fulfilled ─────► 需求已满足
               │
               │  A 修改了 NGD spec
               ▼
           Updating ─────► PRC 重新处理
               │
               │  处理成功
               ▼
           Fulfilled

           (任何阶段，处理失败)
               │
               ▼
           Failed ───────► message 写入失败原因
               │
               │  A 修正条件或集群变化后 PRC 重试
               ▼
           Updating / Fulfilled
```

### 7.2 删除

A 删除 NGD CR -> PRC watch 到 -> 删除对应 NGG CR -> NGG 不再维护

## 8. 多 NGG 场景

### 8.1 为什么需要多个 NGG

不同业务场景可能对节点有不同需求：

| 场景 | 需求 | 对应 NGG |
|---|---|---|
| Spark CPU 作业 | zone-a 内的 CPU 节点 | `ngg-volcano-spark-cpu-zone-a` |
| Spark GPU 作业 | GPU 节点 | `ngg-volcano-spark-gpu` |
| 通用批处理 | 无特殊拓扑要求 | `ngg-volcano-default` |
| Flink 流处理 | 低延迟节点 | `ngg-volcano-flink` |

### 8.2 消费方如何处理多个 NGG

Volcano 插件在 `OnSessionOpen` 时：

1. 通过 informer 缓存列出所有 `spec.schedulerName = volcano` 的 NGG
2. 取所有 NGG 的 `nodes` 列表的**并集**，构建全局候选集
3. 同一节点允许出现在多个 NGG 中；当出现时，score 冲突处理方式见待确认项

```
NGG-1 (zone-a): nodes = [node-01(85), node-02(72)]
NGG-2 (gpu):    nodes = [node-02(90), node-03(68)]

全局候选集 = {node-01: 85, node-02: ??, node-03: 68}
                          ↑ score 冲突，处理方式待确认
```

### 8.3 节点组隔离 vs 共享

- **默认共享**：多个 NGG 的节点取并集，Volcano 在并集内调度
- **可选隔离**：通过 PodGroup annotation 或 label 关联到特定 NGG，由插件 FilterFn 做二次过滤。此功能为后续演进项。

## 9. 时效性设计

### 9.1 数据时效链路

```
负载数据采集        PRC 处理           CRD 写入         informer 传播      插件消费
    │                 │                 │                 │                 │
    ├── 15s 周期 ──►  ├── 过滤+打分 ──► ├── update CR ──► ├── watch 通知 ──► ├── OnSessionOpen
    │                 │                 │                 │                 │
    └── 数据快照时间 (timestamp) ─────────────────────────────────────────► 时效校验
                                                                              │
                                                              当前时间 - timestamp > expirySeconds?
                                                                              │
                                                                         过期 -> 降级/告警
```

### 9.2 时效参数

| 环节 | 时延 | 说明 |
|---|---|---|
| 负载数据采集周期 | 15 秒 | Prometheus scrape interval 或自定义采集 |
| PRC 处理耗时 | < 1 秒 | 内存计算，过滤+打分+资源计算 |
| CRD 写入耗时 | < 1 秒 | 一次 API write |
| informer 缓存传播 | 1-5 秒 | K8s watch 机制延迟 |
| **总滞后** | **15-20 秒** | 从负载数据产生到插件可消费 |
| 插件时效阈值 | 60 秒 | 可配置（`rdp.expirySeconds`） |
| **安全余量** | **约 40 秒** | 60 - 20 = 40 秒 |

## 10. 过滤模型

NGG 只提供经负载感知筛选的节点组，不做容量检查。容量管理是 Volcano 原生 Filter 的职责，NGG 介入会引入两个数据源（真实负载 vs request 累计）的不一致风险。NGG 的 `resources` 字段仅用于信息展示和 ScoreFn 辅助，不用于 Filter 拦截。

## 11. 契约变更管理

### 11.1 变更分类

| 变更类型 | 示例 | 处理方式 |
|---|---|---|
| **兼容变更** | 新增可选字段（如 `nodes[].gpuAvailable`） | 同一 version 内进行，消费方对未知字段忽略 |
| **不兼容变更** | 修改字段语义、删除字段、改变类型 | 升级 `spec.version` 版本号，双方同时升级 |
| **语义变更** | score 计算公式调整 | 不需版本号变更，但需通知评估影响 |

### 11.2 两个 CRD 独立演进

- NGD 的 schema 变更只影响 A-B 接口，C 不感知
- NGG 的 schema 变更只影响 B-C 接口，A 不感知
- 两者可以独立版本化、独立升级

### 11.3 版本兼容矩阵（以 NGG 为例）

| NGG version | PRC 版本 | 插件版本 | 行为 |
|---|---|---|---|
| v1 | v1.x | v1.x | 正常 |
| v1 | v1.x | v2.x | 插件兼容 v1，正常 |
| v2 | v2.x | v1.x | 插件不支持 v2，拒绝调度并报错 |
| v2 | v2.x | v2.x | 正常 |

## 12. 接口约束总结

### 12.1 A（需求方）的承诺

1. NGD `spec.nodeSelector` 使用合法的 LabelSelector 语法
2. 需求变更通过修改 NGD spec 完成，不直接操作 NGG
3. 不修改 NGG 的任何字段
4. NGD 删除意味着不再需要对应节点组，PRC 将删除 NGG

### 12.2 B（PRC / 平台组）的承诺

1. NGG `spec.nodes` 只包含经过拓扑筛选 + 负载感知过滤的节点，过载节点不会出现
2. `spec.timestamp` 每 15 秒更新一次，反映最新负载数据快照时间
3. `spec.source` 如实反映数据来源状态（normal/degraded/disabled）
4. `spec.nodes[].score` 反映节点真实负载空闲度，降序排列
5. 不修改 `status.consumer` 区域
6. NGD spec 变更后在下一次定时更新时生效
7. NGD 删除时删除对应 NGG
8. NGG spec 变更前通知数据组

### 12.3 C（Volcano 插件 / 数据组）的承诺

1. 只在 NGG `spec.nodes` 列表内的节点上做调度决策
2. `FilterFn` 检查节点是否在候选集内，不在则过滤
3. `ScoreFn` 使用 `score x scoreWeight` 作为负载分贡献
4. 不基于 `resources` 字段做 Filter 拦截（容量检查由 Volcano 原生 filter 负责）
5. 不修改 `spec` 区域
6. 定期更新 `status.consumer.acceptedGeneration` 和 `status.consumer.used`
7. NGG 版本不匹配时拒绝调度并报错

### 12.4 双方共同承诺

1. CRD spec 变更需双方协商，单方面不修改
2. 不兼容变更通过 `spec.version` 管理
3. 各自保障己侧组件的可用性，故障时不阻塞对方（降级策略见 TODO）
4. 联合测试验证后部署
5. 跨组件问题联合排查
