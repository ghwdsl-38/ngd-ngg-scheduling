# NGD-NGG 项目代码审查问题与整改方案 v1.0

本文记录本次代码检查发现的问题、拟采用的解决方案和验收要求。**问题 1（Python Worker 超时恢复）、问题 2（Algorithm 镜像构建依赖）已修复并验证；其他问题仍为整改计划，尚未实施。** 下文的复现和检查结果保留修复前的审查记录。

检查范围包括 PRC、Algorithm Server、Python Worker 通信、LLDP 接口选择以及部署构建。不调整联通 NGD/NGG 接口定义，不恢复已移除的调度插件和 Kind Demo。

## 二、问题及拟定解决方案

### 1. Python Worker 超时后的通信恢复

代码位置：[worker.go](../../algorithm_server/go/algorithm/worker.go)，重点是请求加锁、`stdout.Scan()`、`ctx.Done()` 和进程关闭逻辑。

**当前问题**

Go 向 Python 写入 JSONL 请求后，启动协程读取输出。请求超时时，调用方返回并释放锁，但原来的读取协程可能仍在读取共享 stdout。下一次请求又启动读取协程，导致多个协程操作同一个 Scanner。

本次使用真实 Go Worker 通信代码和一个每次延迟约 120 ms 的模拟 Python Worker：首个请求设置 10 ms 超时，随后五次请求各设置 1 s 超时，五次均超时；开启 `-race` 后报告 `Found 8 data race(s)`。

此外，等待互斥锁、写入 stdin 和等待 Python 退出，也需要纳入取消与超时控制，不能只控制读取响应这一步。

**拟定方案**

1. 正常情况下继续复用一个常驻 Python 进程，但每个进程只能有一个通信所有者，串行管理请求和响应。
2. 等待执行的请求支持取消；尚未发送的请求取消时，不终止其他正在执行的请求。
3. 已发送请求出现超时、进程退出或协议错误后，将当前进程标记为不可用，限时终止并回收进程、管道及读取协程。
4. 确认旧读取协程退出后，再使用新进程处理下一请求，避免新旧请求串线。
5. 增加有限重启及退避，限制关闭耗时。不能只加大超时时间，也不能无限等待旧读取完成。

**验收要求**

- 请求 A 超时后，请求 B 可以正常返回，响应 ID 与请求匹配。
- 排队请求取消不影响正在执行的请求。
- Python 卡住、退出、返回非法内容时，服务能够恢复且可以限时关闭。
- `go test -race` 无共享 Scanner 数据竞争，Group1、Group2、Group4 正常路径仍通过。

**本项修复记录（2026-09-05）**

- `worker.go` 使用支持 Context 取消的串行入口，将 stdin 写入和 stdout 读取纳入同一事务；取消执行中的请求会关闭管道、回收进程并等待读写者退出。
- 新进程拥有独立 Scanner 和管道，下一请求按需重启，不自动重放失败请求。健康进程及合法业务错误不触发重启。
- 增加 100 ms 重启退避，每请求最多尝试启动一次；回收等待限时，未回收完成不启动替代进程。关闭操作幂等，父 Context 取消也回收空闲进程。
- 新增 [worker_test.go](../../algorithm_server/go/algorithm/worker_test.go) 和 [异常 Python 测试进程](../../algorithm_server/go/algorithm/testdata/recovery_worker.py)，不修改正式 Python 算法。
- `GOWORK=off go test -mod=vendor -race ./... -count=3` 通过；覆盖重复超时、排队取消、异常输出、进程退出、写阻塞、关闭及重启恢复。
- Group1、Group2、Group4 单次回归均通过，输出业务耗时分别为 124.881 ms、163.888 ms、323.268 ms。此次是功能回归，且与其他检查存在并发，不能作为性能对比结论。
- 实际镜像构建通过：`ngd-ngg-algorithm:workerfix-20260905`。此标签包含 Worker 修复；之前的 `buildfix-20260905` 标签仅包含构建依赖修复。新镜像仅保存在本机数据盘，未推送或部署。

行为、关闭上限及专项测试命令见 [Algorithm README](../../algorithm_server/README.md#python-worker-超时恢复)。本次不修改 PRC、LLDP 和其他四项待整改逻辑，也不替换运行中的服务。

### 2. Algorithm 构建依赖不一致

代码位置：[go.mod](../../algorithm_server/go/go.mod)、[vendor/modules.txt](../../algorithm_server/go/vendor/modules.txt)、[Dockerfile.algorithm](../../Dockerfile.algorithm)。

**当前问题**

`go.mod` 声明的部分依赖与 `vendor/modules.txt` 不一致，包括 `github.com/kr/pretty`、`github.com/rogpeppe/go-internal`、`gopkg.in/check.v1`。当前 Dockerfile 使用 `go build -mod=vendor`，因此受影响。

本次在 Algorithm Go 模块内执行默认测试和显式 `-mod=vendor` 构建，均出现 `inconsistent vendoring`。改用 `-mod=readonly` 的算法包测试通过，但这不能证明镜像构建可用。本次没有完成 Algorithm 镜像构建。

**拟定方案**

使用与镜像一致的 Go 工具链，在 Algorithm 独立模块中整理依赖并重新生成 vendor，审核并一起提交 `go.mod`、`go.sum` 和 vendor 的变化。保留可复现的 vendor 构建方式，不仅手工修改 `modules.txt`，也不通过临时切换在线依赖模式掩盖问题。

实施时拟执行：

```bash
cd /mnt/data0/volcano-scheduler/ngd-ngg-scheduling-demo/algorithm_server/go
GOWORK=off go mod tidy
GOWORK=off go mod vendor
GOWORK=off go test -mod=vendor ./...
GOWORK=off go build -mod=vendor ./cmd/algorithm-server
```

以上是后续整改命令，不是已经完成的修复记录。

**验收要求**

干净检出的代码能够执行 vendor 模式测试和构建，并实际构建 `Dockerfile.algorithm` 镜像。后续发布检查覆盖 PRC、Algorithm、LLDP 三个镜像，不能仅凭包测试通过就判定可部署。

**本项修复记录（2026-09-05）**

使用 Go 1.25.13 执行 `GOWORK=off go mod tidy` 和 `GOWORK=off go mod vendor`，自动重新生成依赖清单。最终仅 `algorithm_server/go/vendor/modules.txt` 增加缺失的三个模块声明；`go.mod`、`go.sum` 和业务代码没有因本次修复发生变化。

- `GOWORK=off go test -mod=vendor ./...`：通过。
- 项目根目录执行 `docker build -f Dockerfile.algorithm -t ngd-ngg-algorithm:buildfix-20260905 .`：通过，镜像中的 vendor 模式二进制编译成功。
- 生成本机镜像 `ngd-ngg-algorithm:buildfix-20260905`，Docker 存储位于 `/mnt/data0/docker-data`。
- 未推送镜像、未部署到集群、未替换运行中的服务。本次未做干净检出或真实集群联调，也未修复其他五项问题。

### 3. PRC 动态资源统计不完整

代码位置：[snapshot.go](../../prc/pkg/controller/snapshot.go) 中的 `buildSchedulerState`；下游使用位置：[node_view_builder.py](../../algorithm_server/python/algorithm_worker/services/node_view_builder.py)。

**当前问题**

目前只累计普通容器的 `resources.requests`，遗漏 Init Container、可重启 Init Sidecar 及 Pod Overhead 的有效资源需求。算法使用这份统计计算剩余资源，因此可能把实际不足的节点判断为可行。

本次调用真实资源统计代码的简单复现：

| Pod 内容 | CPU 请求 |
| --- | ---: |
| 普通容器 | 1 核 |
| 一个普通、非可重启 Init Container | 8 核 |
| Pod Overhead | 100m |
| 当前统计输出 | 1 核 |
| 此例应统计的有效请求 | 8.1 核，即 8100m |

**拟定方案**

优先复用与当前 Kubernetes 依赖版本匹配的 Pod 有效资源请求计算函数，实施时确认具体 API，不另写一套简化公式。需要覆盖普通容器、顺序执行的 Init Container、可重启 Init Sidecar 和 Overhead，并核对当前版本支持的 Pod 级请求、资源调整语义。

继续统计已绑定且尚未释放的资源，保持未绑定 Pod、已终止 Pod 的处理边界明确。这里计算的是调度资源请求，不使用 Prometheus 实时使用量代替。

**验收要求**

上述例子输出 `8100m`；补充内存、多 Init Container、Sidecar、扩展资源等用例。普通 Pod 的原有结果不变；受影响的测试预期应按正确资源语义更新，而不是只修改预期使测试通过。

### 4. 静态快照失败后仍被判为可用

代码位置：[static_snapshot_controller.go](../../prc/pkg/controller/static_snapshot_controller.go) 中的 `StaticSnapshotState.failed` 和静态快照 Reconcile。

**当前问题**

某些失败路径仅记录 `LastError`，不会取消之前的 Ready 状态。例如新拓扑无法解析时，PRC 仍可能将旧快照视为可用。

本次使用真实静态快照 Reconciler、模拟 Kubernetes Client 和模拟 HTTP 响应：先同步合法节点，得到 `ready=true`；随后将该节点的 `leaf-switch-ids` 改成非法 JSON，再次处理后仍为 `ready=true`，同时已记录拓扑解析错误。

问题不是“不能保留旧缓存”，而是“保留旧缓存后仍允许它作为当前有效数据参与计算”。

**拟定方案**

- 区分“最后一次成功的数据”与“当前是否允许使用”。
- 已确认拓扑非法、节点集合失效或无可用节点时，立即将当前快照标记为不可用；旧数据只保留用于排障。
- 第一版对读取、构建或同步失败采用保守的暂停计算策略；如果后续需要容忍短暂 API 故障，再单独设计有上限的旧数据有效期，不能无限保持 Ready。
- 新快照完成校验并获得 Algorithm 的 Hash、实例身份确认后，恢复 Ready，并恢复等待中的任务。

**验收要求**

合法输入 → 非法输入 → 修复输入，Ready 应依次为真、假、真。覆盖节点删除、拓扑缺失、Algorithm 重启和同步失败，确认暂停期间不会继续以已失效拓扑产生结果。

### 5. 显式指定 Bond 主接口时的采集范围错误

代码位置：[discovery.go](../../topology_agent/pkg/bond/discovery.go) 中的 `SelectInterfaces`。

**当前问题**

指定 `--interfaces=bond0` 后，代码会先将 Bond 展开为成员网卡；随后普通接口回退逻辑又把 `bond0` 本身加入采集集合，因为它不是已知的从接口。

本次模拟主备 Bond：成员为 `eth0/eth1`，当前主网卡为 `eth0`。实际返回 `bond0（direct）+ eth0（active-backup）`，预期应仅返回 `eth0`。这可能造成多余采集、重复观察，或等待主接口上的 LLDP 数据直到监听超时。

**拟定方案**

显式区分 Bond 主接口、从接口和独立物理网卡。Bond 主接口只负责选择和展开，不再进入普通网卡回退集合。没有可用成员时报告无可用采集接口，不把主接口伪装成普通网卡继续执行。

本项不改变已经确认的 Bond 模式处理策略，只修正接口选择范围。

**验收要求**

- 主备模式指定 `bond0`：仅选择当前有效主网卡。
- 负载模式指定 `bond0`：选择符合条件的成员网卡，不包含主接口本身。
- 覆盖显式指定从接口、普通网卡、成员链路断开、没有有效主网卡等情况，并回归 Group7。

### 6. NGD 变化与结果提交之间的并发风险

代码位置：[prc_controller.go](../../prc/pkg/controller/prc_controller.go) 中的 `demandStillCurrent`、`upsertGrant`、`applyStatus`，以及 [refresh_controller.go](../../prc/pkg/controller/refresh_controller.go) 中的 `deleteGrant`。

**当前风险，尚未复现**

当前已经有 UID、generation 检查和任务取消机制，但最终检查可能读到 Manager 缓存；部分写状态操作未携带对象版本约束，删除 NGG 主要按名称执行。

如果计算期间 NGD 更新，或删除后又创建同名 NGD，旧计算结果与新对象之间可能出现交错。取消请求也不能撤销已经被 API Server 接受的写入。

**拟定方案**

1. 最终提交前通过 `Manager.GetAPIReader()` 直接读取 NGD，检查 UID、generation 和删除状态。
2. 状态更新使用适当的资源版本并发保护，确认仍是同一个对象。发生冲突时丢弃过期结果并重新读取，不强行重放旧状态。
3. 更新 NGG 时核对现有 NGG 的 UID、资源版本和所属 NGD；删除时核对归属并使用 UID 前置条件，避免误删同名新对象。
4. 继续只管理 PRC 负责的字段，不覆盖消费方维护的状态。
5. 保持按任务串行、更新取消及幂等补偿，覆盖成功和失败回写路径。

直接读取只能缩小竞态窗口，**不能让 NGD 与 NGG 两个对象的修改变成原子事务**。跨对象一致性仍需靠版本检查、幂等和后续处理收敛，不能承诺完全没有中间状态。

这些机制使用 Kubernetes 已有 metadata，不需要给联通 CRD 新增自定义 generation 字段。

**验收要求**

使用 envtest 的真实 API Server/etcd，通过明确的同步点暂停结果提交，分别模拟 NGD 更新、删除后同名重建、消费方并发更新状态，以及旧删除事件遇到新 NGG。验证旧结果不会成为最终有效结果、新对象不会被误删、消费方字段不会被覆盖。

## 三、实施顺序与测试安排

| 顺序 | 整改内容 | 主要验证方式 |
| --- | --- | --- |
| 1 | 修复 vendor，恢复可复现构建 | 模块测试、二进制构建、镜像构建 |
| 2 | 修复 Worker 超时与进程恢复 | 慢响应/异常 Python、取消测试、Race 检查 |

优先使用本地 Mock 和 envtest，不需要真实创建大规模 Kubernetes 节点。功能正确性先通过，再比较耗时；Race 检查和 Debug 下的耗时不作为性能结果。

新增复现应转为仓库内的自动化测试，保留输入、预期、实际输出和运行命令。本次临时复现程序不是最终交付的测试入口。
