# NGD/NGG 两层调度 Demo：从零实现与复现说明

> 版本提示：本文中的 `make run` 和 Top-3 + activeGroup 步骤对应旧 Demo 接口。2026-08-19 的当前源码已开始输出联通正式扁平 NGG，调度插件和演示脚本尚未完成新 NGG 消费适配，本轮也按要求未部署、未测试。先阅读 `Prometheus三层拓扑与联通正式NGG改造说明v2.1.md`，不要用本文旧运行结果验收新链路。

## 1. 要解决的问题

普通 Kubernetes/Volcano 调度器直接在全体可用 Node 中为 Pod 选最终节点。本 Demo 在它们上面增加一个任务级第一层：

```text
第一层：根据整个任务需求划分和排序候选节点组
第二层：只在当前授权节点组内为每个Pod选择最终Node
```

第一层不绑定 Pod，也不预留资源；第二层仍负责 Taint/Toleration、Affinity、Volume、HostPort、实际资源冲突和 Bind。

## 2. 总体结构

```mermaid
flowchart TB
    STATIC[Leaf到Border到Core静态JSON] -->|步骤1a：提供上层静态拓扑| AGENT[Go LLDP Agent DaemonSet]
    WORKER[9个Worker] -->|步骤1b：模拟种子或物理LLDP 0x88CC<br/>采集Node到Leaf| AGENT
    AGENT -->|步骤2：写入Leaf/Border/Core| LABEL[Node Labels]
    USER[用户或任务系统] -->|步骤3a：提交任务级资源与拓扑要求| NGD[NodeGroupDemand]
    USER -->|步骤3b：提交实际工作负载| JOB[VolcanoJob或Kubernetes Job]

    LABEL -->|步骤2：持久化拓扑| API[Kubernetes API Server]
    NGD -->|步骤3a：写入Kubernetes| API
    API -->|步骤4a：Watch Node与拓扑变化| STATIC_SYNC[PRC静态快照Controller]
    API -->|步骤4b：Watch NGD及任务动态变化| PRC[PRC NGD Reconciler]
    JOB -->|步骤4b：Controller创建| POD[待调度Pod]

    STATIC_SYNC -->|步骤5a：独立PUT静态Node快照<br/>内容Hash作为身份| ALG[Go Algorithm API Server<br/>HTTP + 缓存 + 编排]
    PRC -->|步骤5b：POST任务需求、当次动态状态<br/>及已确认snapshotId| ALG
    PROM[Prometheus] -->|步骤5c：Go后台周期采集| MCACHE[Go进程内指标缓存]
    MCACHE -->|步骤5c：提供实时指标快照| ALG
    ALG -->|步骤6：发送完整上下文<br/>本地JSON-RPC| PY[单一Python算法Worker]
    PY -->|步骤7a：返回分数降序稳定Top-3| ALG
    ALG -->|步骤7b：保持分数和原顺序| PRC
    PRC -->|步骤8：创建或更新授权结果| NGG[NodeGroupGrant<br/>候选组+唯一activeGroup]

    NGG -->|步骤9a：Informer读取当前授权组| VP[Volcano NGG插件]
    NGG -->|步骤9a：Informer读取当前授权组| KP[kube-scheduler NGG插件]
    POD -->|步骤9b：进入第二层调度| VP
    POD -->|步骤9b：进入第二层调度| KP
    VP -->|步骤9c：只放行当前组Node| VN[Volcano原生Gang/Predicates/Score/Bind]
    KP -->|步骤9c：只放行当前组Node| KN[kube-scheduler原生Score/Bind]
    VN -->|步骤10：完成Pod绑定| NODE[最终Node]
    KN -->|步骤10：完成Pod绑定| NODE
```

步骤说明：

1. Go LLDP Agent 采集 Node→Leaf，并使用静态 JSON 补齐 Leaf→Border→Core；
2. Agent 将完整三层拓扑写入 Node Label，由 Kubernetes 持久化；
3. 用户同时提交任务级需求 NGD 和实际工作负载 Job；
4. PRC的静态Controller Watch Node/拓扑，NGD Reconciler Watch任务及动态资源变化；Job Controller创建待调度Pod；
5. 静态Controller在任务到达前独立维护Algorithm静态Hash快照；NGD到达时只发送任务需求、当次动态状态及已确认`snapshotId`，Algorithm同时读取自身缓存的Prometheus指标快照；
6. Go Algorithm 将完整计算上下文发送给单一 Python Worker；
7. Python 完成过滤、分组和评分，Go 保持分数与 Top-3 顺序返回 PRC；
8. PRC 将候选组和唯一 `activeGroupRef` 写入 NGG；
9. Volcano 或 kube-scheduler 插件读取 NGG，只放行当前激活组中的 Node；
10. 原生调度流程继续执行 Score 和 Bind，将 Pod 绑定到最终 Node。

## 3. 集群与网络拓扑

Kind 集群名为 `volcano-ngd-ngg-v2-demo`，包含 1 个 Control Plane 和 9 个 Worker：

```text
                            core-0
                    /          |          \
             switch-a       switch-b       switch-c
             /  |  \          /  \        /  |  |  \
       worker-01 02 03   worker-04 05  worker-06 07 08 09
```

| 接入交换机 | Worker | 模拟链路         |
| ---------- | -----: | ---------------- |
| switch-a   |      3 | 20 Gbps / 1.5 ms |
| switch-b   |      2 | 10 Gbps / 5 ms   |
| switch-c   |      4 | 25 Gbps / 1 ms   |

Kind 使用 Go LLDP Agent 的 Simulated 模式。物理集群切换为 LLDP 模式后，Agent 通过 `hostNetwork + NET_RAW` 监听 `0x88CC` 帧；Node Label 之后的 PRC、Algorithm、NGG 和调度插件无需改变。

## 4. 三个 CR

### 4.1 Node元数据：一个Node的直连Leaf事实

```text
topology.demo.ngg.io/leaf-switch=switch-a
topology.demo.ngg.io/leaf-set-id=<内容Hash>
topology.demo.ngg.io/leaf-count=1
```

完整Leaf列表、远端端口、本地网卡、Bond信息和采集时间写在Annotation中。Border、Spine、机房等上层拓扑只保存在Algorithm配置。当前PRC不注册、Watch或读取`NodeNetworkTopology`。

### 4.2 NGD：任务向第一层提出的需求

```yaml
spec:
  taskRef:
    apiVersion: batch.volcano.sh/v1alpha1 # 也支持batch/v1
    kind: Job
    name: ngg-topology
  schedulerName: volcano                # 或ngg-scheduler
  podSets:
  - name: worker
    replicas: 4
    minAvailable: 4
    resourcesPerPod: {cpu: 100m, memory: 64Mi}
  nodeRequirements:
    nodeSelector: {demo.ngg/worker: "true"}
  topologyRequirement: {level: leafGroup, mode: same}
  grantPolicy:
    maxCandidateGroups: 3
    groupAttemptTimeoutSeconds: 15
    ttlSeconds: 600
```

Volcano 输入为 `manifests/topology-demand.yaml`；Kubernetes Job 输入为 `manifests/kubernetes-demand.yaml`。

### 4.3 NGG：第一层给第二层的授权

```yaml
spec:
  candidateNodeGroups:
  - {rank: 1, groupId: switch-c, groupScore: 100, nodes: [...]}
  - {rank: 2, groupId: switch-a, groupScore: 92.8, nodes: [...]}
  - {rank: 3, groupId: switch-b, groupScore: 80.2, nodes: [...]}
  activeGroupRef: {rank: 2, groupId: switch-a}
  groupAttemptPolicy: {timeoutSeconds: 15, lockAfterFirstBind: true}
  dataVersions:
    nodeStaticSnapshotId: sha256:...
    schedulerStateSnapshotId: sha256:...
    metricSnapshotId: sha256:...
  revision: 2
  validUntil: "..."
status:
  phase: Active
  activeGroupState: Locked
  boundPodCount: 4
  observedRevision: 2
```

NGG 最多保存 3 组，但只有 `activeGroupRef` 指向的一组有效。两个插件都不会把三组 Node 合并使用。

## 5. Go PRC 的实现

正式 PRC 位于 `prc/`，使用 Go 1.25、Kubebuilder 工程结构和 controller-runtime v0.23.1。

主要文件：

- `prc/cmd/main.go`：Manager、leader election、健康检查和 Controller 注册；
- `prc/pkg/controller/static_snapshot_controller.go`：只Watch Node静态字段、维护静态Hash并确认Algorithm缓存；
- `prc/pkg/controller/prc_controller.go`：NGD reconcile、NGG写入、状态机和重算策略；
- `prc/pkg/controller/snapshot.go`：静态快照、动态状态、内容Hash和直接Owner UID关联；
- `prc/pkg/controller/algorithm_client.go`：Algorithm HTTP客户端及静态缓存状态查询。

Manager内注册静态快照、NGD事件和刷新Controller：

- `NodeStaticSnapshotReconciler`只监听Node容量、Label和Leaf Annotation变化，独立构造并同步静态快照；
- `NodeGroupDemandReconciler`只处理NGD创建、generation变化和删除；
- `RefreshScheduler`与`RefreshReconciler`使用controller-runtime原生队列周期执行Demand Processor。

周期刷新负责：

- Pending、Unsatisfied 在资源或拓扑内容变化时重新计算；
- 到达重试时间的 Degraded 会重新调用 Algorithm；
- 未锁定 Active NGG 在候选失效、静态 Hash 变化、动态状态变化或 TTL 临近时重算；
- 已有绑定 Pod 的 Locked NGG 不自动换组，节点异常时只标记 Degraded。

旧 Python PRC 仍保留在 `src/ngd_ngg_demo/controller.py`，镜像入口备份为 `Dockerfile.prc-python-legacy`，但正式 Deployment 已使用 `ngd-ngg-prc:v0.3.0` Go 二进制。

## 6. PRC 与 Algorithm 的协议

### 静态快照

独立`NodeStaticSnapshotReconciler`优先从Node的`leaf-switch-ids` Annotation构造静态快照，并兼容单值`leaf-switch` Label；缺失时跳过该Node，不回退旧NNT。Node Watch只接受创建、删除、Label、相关Annotation或Allocatable变化，忽略不影响静态内容的心跳/ResourceVersion更新：

- Node name、UID、创建时间；
- Allocatable、Labels；
- `leafSwitchIds`、直连链路明细；
- `topologyVersion=node-leaf-set-v2`。

对规范化 JSON 计算 SHA-256，通过：

```text
PUT /internal/v1/node-static-snapshots/{snapshotId}
```

同步给Algorithm。Algorithm重新计算checksum，只在一致时ACK，并在进程内保留current/previous两个不同版本。相同Hash时Controller只查询远端缓存状态；发现Algorithm重启或缓存丢失才重新PUT。NGD Reconciler不构造或上传静态快照，只使用`StaticSnapshotState`中最近一次确认的`snapshotId`；尚未Ready时故障关闭并重试。

### 动态状态

PRC 每次任务请求发送：

- Node UID 和 `inUse` 使用标记；
- NGD PodSets、Selector、拓扑要求和算法参数。

`cache/scheduler_state.py` 只负责校验和规范化本次请求，不保存版本、不做增量同步，也不把动态状态放入跨请求全局缓存。

## 7. Algorithm 与 Prometheus 缓存

Algorithm 位于 `algorithm_server/python/algorithm_worker/`：

1. `requirement.py` 通过 NodeViewBuilder 排除 `inUse=true`、Selector 不匹配或单 Pod 资源不满足的 Node；
2. `topology.py` 按 Core Switch、Leaf Switch、Node 三层拓扑形成候选组；
3. 检查每组能否容纳 PodSet 的 `minAvailable`；
4. `loadbalance.py` 按配置 Profile 结合 Prometheus 指标和拓扑质量评分；
5. 按 `groupScore` 降序、`groupId` 稳定排序；
6. 最多返回 3 个 `candidateNodeGroups`。

PRC 只校验结果，不修改分数、不重新排序。

`metrics.py` 在 Algorithm 进程内保存 Prometheus current/previous 快照。Kind 集群内已部署 Prometheus、kube-state-metrics 和仅覆盖 9 个 Worker 的 node-exporter。Algorithm 使用集群内 Service 地址每 15 秒查询 Node CPU/内存利用率，与PRC Reconcile周期一致；调度请求只读内存快照，查询失败则保留最后一次成功快照并标记 degraded。正常实跑返回内容 Hash 形式的 `metricSnapshotId`。

整个方案不引入 Redis、Kafka或跨 Pod 共享内存，Algorithm 第一版固定单副本。

## 8. 候选组状态机

```mermaid
stateDiagram-v2
    [*] --> TryingRank1: 创建NGG
    TryingRank1 --> TryingRank2: 超时且boundPodCount=0
    TryingRank2 --> TryingRank3: 超时且boundPodCount=0
    TryingRank1 --> Locked: 任意Pod绑定
    TryingRank2 --> Locked: 任意Pod绑定
    TryingRank3 --> Locked: 任意Pod绑定
    TryingRank3 --> Exhausted: 三组均失败且零绑定
    Exhausted --> TryingRank1: Node/Pod/拓扑内容变化后重算
    Locked --> Locked: 同一NGD generation内不跨组
```

关键规则：

- 超时不是充分条件，必须同时满足“一个任务 Pod 都没有绑定”；
- 首个 Pod 一旦绑定，当前组立刻 Locked；
- 全部候选失败时 NGG 为 `Inactive/Exhausted`、NGD 为 `Unsatisfied`；
- 数据内容未变化时 Exhausted 不做周期性空转计算；
- NGD generation 改变后可以生成新一轮候选组。

## 9. 两个第二层插件

### Volcano

`plugin/nodegroupgrant/` 被编译进 Volcano v1.15.0 `vc-scheduler`。通过后继续执行 Volcano 原生 Gang、Predicates、NodeOrder 和 Bind。

### kube-scheduler

`plugin/kubescheduler/nodegroupgrant/` 实现 Kubernetes v1.35 Filter 插件；`cmd/ngg-scheduler/main.go` 使用 `app.WithPlugin` 注册进自定义二进制。Demo 以第二个 scheduler profile 运行，名称为 `ngg-scheduler`，不会替换控制面的默认 kube-scheduler。

两个插件采用相同 Fail Closed 校验：

- 只处理带 `scheduling.demo.ngg.io/node-group-demand` Annotation 的 Pod；
- NGG 必须 Active，状态为 Trying 或 Locked；
- generation、revision、TTL 必须有效；
- Pod schedulerName 和任务直接 Owner UID 必须匹配；
- 只允许 activeGroup 中 name、UID 均匹配的 Node。

没有上述 Annotation 的普通 Pod 不受 NGG 限制。

## 12. 当前边界

- Kind 中 LLDP 为模拟数据，真实 `0x88CC` 模式需在物理网络验证；
- Kind 已接入 Prometheus 并完成演示验证；目标物理集群的 exporter 部署方式、PromQL 和 Node Label 映射仍需按现场监控体系确认；
- Taint、Toleration、Affinity、Volume 和 HostPort 由第二层处理；
- NGG 是候选边界，不是资源预留；并发任务的最终资源冲突仍由原生调度器判断；
- Algorithm 当前为单副本进程内缓存，扩为多副本时需要另行设计一致性方案。
