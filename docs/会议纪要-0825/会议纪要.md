
会议主题：NGD算法实现与单元测试评审

发言人：曾楷、高宏伟

会议摘要：本次会议评审了 NGD 算法实现与 Go 单元测试，确认了 NGG 动态更新机制及拓扑权重配置方案，并针对测试数据异常与性能瓶颈进行了排查，要求补充流程图与统计报告。

一、NGD 算法实现与数据对齐
针对 NGD 的算法实现，双方就数据源对齐与字段处理达成一致：

1. 数据源版本确认
   严格对齐 Git 版本：高宏伟确认当前开发严格对齐 Git 仓库中上传的 NGD 版本，尽管南华老师有更新版本，但为确保读取兼容性，决定先按旧版进行开发。
   字段预留与扩展：目前拓扑结构已实现，子网亲和性网段与可达性字段已传入 Python 算法端，后续若需补充配置信息，可直接在 Python 端进行扩展。
2. 输出结果规范
   NGG 生成格式：NGG 输出为 JSON 格式，包含可用资源与拓扑结构等信息，目前仅生成一组数据。
   字段映射调整：针对 NGG 中的状态字段，曾楷要求将原有的  `deactive` 改为 `Failed` 以符合后续设计规范。
   二、Go 单元测试架构与覆盖率
   高宏伟汇报了 Go 单元测试的架构设计，共分为四组测试用例，覆盖了从 PRC 调用到全链路集成的不同层级：
3. 测试分层设计
   接口层测试（Group 1）：测试 Go 调用 Python 的接口逻辑，确保 PRC 请求与 API Server 的交互正常。
   Mock 层测试（Group 2 & 3）：Group 2 测试 PRC 发起请求到算法返回的完整流程；Group 3 在 PRC 调用算法时进行 Mock，验证单 PRC 逻辑。
   集成层测试（Group 4）：除 Prometheus 和 K8s 模拟外，其他组件均使用真实环境，测试全链路集成效果。
4. 测试环境与数据
   Mock 数据规模：测试环境模拟了 1000 个节点，并 Mock 了 Prometheus 和 K8s 的相关数据。
   目录结构规范：测试目录包含 `golden`（期望与实际输出对比）、`fixture`（模拟数据准备）及具体的测试文件。
   三、NGG 动态更新机制与策略
   针对 NGG 的时效性问题，会议明确了动态更新的实现逻辑与资源调度策略：
5. 生命周期管理
   持续监控机制：NGG 不应在生成后固定不变，而是需要持续监控 NGD 状态。只要 NGD 存活，就持续更新 NGG 的时间戳。
   时间戳校验：NGG 的时间戳需与本地时间进行比对，若时间戳过旧（如超过 30 分钟），则认为 PRC 异常，需重新生成。
6. 资源变更策略
   渐进式变更需求：业务方要求当资源池发生变化时（如从 Node 1-6 变为 Node 7-12），不应一次性全量替换，而应采用“淘汰最差、引入最优”的渐进式变更策略，以避免调度混乱。
   拓扑与资源的权衡：高宏伟指出全量替换在拓扑计算上可能更高效，而曾楷强调资源充足性是硬性条件，建议通过配置权重来解决优先级问题，两者应并列考虑。
   四、性能测试与排查
   在性能测试环节，发现部分测试组耗时异常，双方进行了初步排查并制定了优化计划：
7. 性能数据异常
   Group 4 耗时过长：集成测试（Group 4）耗时约 3 秒，远超预期。曾楷指出 Python 算法慢是可接受的，但当前耗时仍不合理。
   Group 3 异常耗时：Mock 测试（Group 3）也出现了较长的耗时，这与仅增加 PRC 流程的预期不符，怀疑存在性能瓶颈。
8. 排查与优化方向
   瓶颈定位：要求高宏伟在 Group 4 测试中增加分段计时，定位具体卡顿环节（如算法计算、PRC 通信等）。
   多维度压测：计划补充不同节点规模（如 6、60、600 个节点）的测试，并统计 P90、P95 等指标，以获取更准确的性能基线。
